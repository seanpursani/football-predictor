## Challenges & Growth Areas

1. **Deno/Node dual-runtime friction accumulated across stories**
   - The `typeof Deno !== 'undefined'` guard, `.ts` extension imports, `getEnv` helper, `moduleNameMapper` for `esm.sh` URLs, and `allowImportingTsExtensions` tsconfig flag — all had to be discovered and refined incrementally across Stories 3.1, 3.2, 3.3.
   - The Epic 2 prep item ("Supabase Edge Function + Deno testing patterns review") was not fully completed before stories started. The team learned on the job.
   - By Story 3.4 the patterns were stable and natural, but the cost was visible: each story's debug log had at least one Deno compatibility note.

2. **Silent failure pattern — systemic optimism about error paths**
   - Four separate instances of error values being swallowed without surfacing:
     - `push-sender.ts`: orphaned Expo Push API tickets silently counted as `sent` (Story 3.2)
     - `ingest-events`: `run-scoring` invocation failure returned overall success (Story 3.3)
     - `ingest-events`: `scoring_errors` insert failure was swallowed (Story 3.3)
     - `apply_cron_schedules()`: `current_setting()` without `missing_ok` would error on fresh DB reset (Story 3.4)
   - All were caught in code review, but the pattern suggests the team defaulted to optimistic error handling rather than defensive returns.

3. **DB status value case mismatch (Story 3.2)**
   - Story ACs and dev notes used `'Building'` (PascalCase). The DB constraint enforces `'building'` (lowercase). Only caught during implementation, causing a debug detour.
   - Root cause: story creation process doesn't cross-reference DB enum constraints from the Drizzle schema.

4. **Story 3.1 status tracking gap**
   - Story 3.1's story file still shows `Status: review` while `sprint-status.yaml` marks it `done`. Minor tracking discipline slip — the code review findings were applied, but the story file was not updated to reflect completion.

5. **🚨 Critical Deferred: Double-invocation race in gameweek completion detection (Story 3.3)**
   - Two concurrent `ingest-events` calls completing simultaneously could both pass the `allFixtures.every(f => f.events_ingested || f.is_postponed)` check before either writes `events_ingested = true`. Both would invoke `run-scoring`, potentially double-scoring the entire gameweek.
   - This was deferred because the fix requires a DB-level change outside the story's scope (an advisory lock or `scoring_triggered` flag on `gameweeks`).
   - **Production risk:** Until this is resolved, any week with near-simultaneous final match completions could trigger double-scoring. This is a data integrity issue.

## Key Insights

1. **Knowledge preparation debt is velocity drag** — The Deno patterns review was flagged in Epic 2's retro as pre-Epic 3 prep. It wasn't done. The cost was spread across all 5 stories as incremental friction, not concentrated as one learning spike. One focused session before Story 3.1 would have saved cumulative debug time.

2. **Pattern libraries need to be made explicit, not just learned** — The handler pattern, `getEnv` helper, and mock strategy were all learned organically. By Story 3.4 they were de facto standards. They should be documented as official team conventions, not just "previous story learnings" in individual story files.

3. **Defensive returns need to be a default habit, not a review catch** — In an event-driven backend, silent failures are more dangerous than in mobile UI code. `supabase.functions.invoke()`, `scoring_errors` inserts, and push delivery calls all need explicit error handling by default.

4. **The double-invocation race is the outstanding production blocker from this epic** — Everything else was resolved or acceptably deferred. This one has a concrete path to production impact.

## Significant Discoveries

### Discovery: Double-Invocation Race in Gameweek Completion Detection

**What:** `ingest-events` checks gameweek completion with a non-atomic read (`allFixtures.every(...)`) and then separately invokes `run-scoring`. Two concurrent calls completing at the same time can both pass the check before either writes back, resulting in two `run-scoring` invocations.

**Deferred reasoning (Story 3.3):** The fix requires a DB-level solution (advisory lock or `scoring_triggered` column) that is outside an ingestion story's scope.

**Impact on production:** If two matches in a gameweek complete near-simultaneously (common in a typical football Saturday), the race window is real. Double-scoring would corrupt all `scoring_results`, `leaderboard_entries`, and the results push notification would fire twice.

**Recommended action (Action #1 above):** Add `scoring_triggered boolean DEFAULT false` to `gameweeks` and use an atomic UPDATE as the completion gate. No application-level lock needed.
