## Successes & Strengths

1. **Clean architectural discipline** — `useAuthState` + TanStack Query pattern held consistent across all 5 stories; server state never leaked into Zustand; Supabase singleton never re-initialised.
2. **Progressive story learning** — "Previous Story Learnings" sections in 2-2 through 2-5 captured lessons in-flight; `jest.mock()` outer-variable issue was documented and did not recur as a surprise after 2-1.
3. **Database-layer RLS** — Story 2-4 delivered deadline-aware SELECT policies, deadline write-lock enforcement, admin bypass, and 11 integration tests. Production-grade DB security established before predictions are ever written.
4. **Zero hard blockers** — All 5 stories flowed sequentially without external dependencies causing stalls.
5. **`[Review][Defer]` audit trail** — Every code review finding was classified and tracked inside the story file. This created a reliable technical debt register.

## Challenges & Growth Areas

1. **`_layout.tsx` deferred debt accumulated across 3 stories**
   - `useUserQuery` error state returns `null` with no error UI (first flagged 2-1, still open at 2-5)
   - `upsertUser` missing from `useEffect` dependency array (2-1, deferred throughout)
   - `upsertUser` failure leaves `userRecord` null, bypassing the onboarding gate (flagged 2-5)
   - Root cause: treating these as "pre-existing" rather than owning the file.

2. **Supabase mock chain reinvented every story**
   - `supabase.from().update().eq()` mock appeared as a "lesson" in 2-2, 2-3, 2-4, and 2-5.
   - No shared mock factory was ever created. Each story copy-pasted the chain.

3. **`screens.test.ts` required manual mock additions in 3 consecutive stories (2-2, 2-3, 2-5)**
   - The bare `require(screenPath)` pattern is environment-sensitive and not isolated.
   - Every new module import in a screen broke this test without warning.

4. **High review finding volume in 2-4 (RLS)**
   - 9 patches were required post-implementation: wrong JWT path in `is_admin()`, missing `WITH CHECK` on UPDATE policies, broken test helper column names.
   - Indicates RLS policy design benefit from a pre-implementation checklist or reviewer template.

5. **🚨 Critical: `users` table RLS INSERT gap**
   - Story 2-4 enabled RLS on `users` but added no INSERT policy.
   - Story 2-1 mobile client uses `supabase.upsert()` which requires INSERT permission.
   - **New user sign-in will silently fail to create the `users` row in production.**
   - This was not caught because no integration test covers the new-user sign-in path against a live RLS-enabled DB.

---

## Key Insights

1. **Deferred issues in shared files compound** — When the same file (`_layout.tsx`) carries defers across 3 stories, it needs a focused cleanup story, not more deferrals.
2. **Test infrastructure debt is expensive** — Reinventing the Supabase mock chain 4 times and patching `screens.test.ts` 3 times cost more effort than building the shared factory once in 2-1.
3. **RLS requires end-to-end coverage** — Unit tests alone cannot catch a missing INSERT policy. Integration tests must exercise the full user creation path on a live DB.
4. **Epic 3 is a significant context shift** — Supabase Edge Functions (Deno), external API clients, cron scheduling. None of Epic 2's mobile Jest patterns apply directly. Preparation is required.

## Significant Discoveries

### Discovery: `users` table RLS INSERT gap

**What:** `ALTER TABLE users ENABLE ROW LEVEL SECURITY` was applied in Story 2-4. No INSERT policy was added. Story 2-1 mobile client calls `supabase.upsert()` on `users` on first sign-in. With RLS active and no INSERT policy, the upsert is silently blocked.

**Impact on Epic 3:** Epic 3 is backend-only and does not touch user creation — but this bug must be fixed before any production release, and the Epic 2 foundation cannot be considered production-ready without it.

**Recommended action:** `0003_users_insert_policy.sql` migration (3 lines of SQL). Add integration test covering new-user full sign-in path. Do not start Epic 3 until complete.
